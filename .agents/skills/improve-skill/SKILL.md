# improve-skill

## 1. 目的

振り返りによって発見された問題を、業務スキルの改善につなげる。

本スキルの責務は以下の6つとする。

1. retro が作成した振り返りレポートを取得する。
2. Problem と Try の対応関係および妥当性を検証する。
3. 対象スキルの改善候補を作成する。
4. 改善内容の品質検証と eval-skill による再評価を実施する。
5. 評価に合格した改善内容を正式版に反映し、Pull Request を作成する。
6. 明示的に許可された場合のみ自動マージする。

本スキルは、改善の必要性がない場合に無理に変更を作成しない。

## 2. トリガー

以下の条件を満たした場合に実行する。

- retro の処理が完了している。
- retro から明示的に本スキルが呼び出されている。
- 対象となる振り返りレポートが特定できる。

### 実行対象外

以下の場合は改善処理を開始しない。

- 振り返りレポートが存在しない。
- 対象スキルを特定できない。
- 必要な入力情報が不足している。
- 改善対象が存在しない。

実行できない場合は、理由と不足情報を呼び出し元に返す。

## 3. 入力

以下の情報を呼び出し元から受け取る。

| 入力 | 必須 | 説明 |
|---|---|---|
| 振り返りレポート | 必須 | retro が生成したKPTファイルのパス |
| 対象スキル名 | 必須 | 改善するスキル名 |
| 対象スキルのパス | 必須 | 正式版 SKILL.md のファイルパス |
| eval-skill | 必須 | 改善後の評価に使用するスキル |
| 改善対象の範囲 | 任意 | 変更を許可するファイルや項目 |
| 出力ルート | 任意 | 改善成果物の保存先。未指定時は `skill-development/` |
| 自動マージ許可 | 任意 | 自動マージを許可する明示的な設定 |

### 入力取得ルール

1. retro から渡されたファイルパスを最優先する。
2. 「直近の振り返りファイル」を独自に検索して代用しない。
3. 指定された振り返りレポートが存在しない場合は処理を中断する。
4. 対象スキルの SKILL.md を読み込んでから変更案を作成する。
5. 関連する評価基準やテストケースが存在する場合は、それらも確認する。
6. 複数の対象スキルが候補となる場合は、推測で選択せず確認する。
7. 出力ルートが指定されていない場合は `skill-development/` を使用する。
8. 出力ルートが存在しない場合は作成する。

## 4. 成果物と出力先

本スキルが生成する成果物の保存先を以下のように定義する。

### 4.1 ディレクトリ構成

リポジトリのルートディレクトリを基準として、以下の構成を使用する。

```text
repository/
├── .agents/
│   └── skills/
│       └── <skill-name>/
│           └── SKILL.md
│
├── skill-development/
│   ├── proposals/
│   │   └── <skill-name>/
│   │       └── <run-id>/
│   │           └── SKILL.md
│   │
│   ├── evaluations/
│   │   └── <skill-name>/
│   │       └── <run-id>/
│   │           └── evaluation.md
│   │
│   └── reports/
│       └── <skill-name>/
│           └── <run-id>/
│               └── improvement.md
│
└── docs/
    └── retrospectives/
```

`<skill-name>` は改善対象のスキル名とする。

`<run-id>` は1回の改善処理を識別するためのIDとする。

形式：

`YYYYMMDD-HHMMSS`

例：

`20261111-153000`

### 4.2 各成果物の役割

| 成果物 | 保存先 | 内容 |
|---|---|---|
| 改善候補 | `proposals/` | 改善後の SKILL.md |
| 評価レポート | `evaluations/` | eval-skill の評価結果 |
| 改善レポート | `reports/` | 改善内容と処理結果 |
| 正式版 | 元の対象スキルのパス | 評価合格後の SKILL.md |

### 4.3 出力先の絶対ルール

以下を必ず守る。

1. 改善候補は必ず `proposals/` に保存する。
2. 改善候補を正式版と混同しない。
3. 評価結果は必ず `evaluations/` に保存する。
4. 改善処理の最終結果は必ず `reports/` に保存する。
5. 評価合格前に正式版を変更しない。
6. 改善候補と正式版を同じファイルにしない。
7. 既存の成果物を無断で上書きしない。
8. 出力先が存在しない場合は必要なディレクトリを作成する。
9. 書き込みに失敗した場合は、別の場所へ勝手に出力先を変更しない。
10. 出力したファイルの存在を確認してから成功と報告する。

### 4.4 run-id の管理

改善処理の開始時に run-id を1つ生成する。

以降、同じ改善処理で生成するすべての成果物に同じ run-id を使用する。

例：

```text
skill-development/
├── proposals/
│   └── bugfix/
│       └── 20261111-153000/
│           └── SKILL.md
│
├── evaluations/
│   └── bugfix/
│       └── 20261111-153000/
│           └── evaluation.md
│
└── reports/
    └── bugfix/
        └── 20261111-153000/
            └── improvement.md
```

同じ run-id の出力先がすでに存在する場合は、既存ファイルを上書きせず、新しい run-id を生成する。

## 5. 改善処理の基本ルール

以下を必ず守る。

1. Problem と Try の対応関係を維持する。
2. Try を無条件に採用しない。
3. 改善対象のスキルだけを変更する。
4. 改善に必要な根拠がない場合は変更しない。
5. 既存の正常な動作を維持する。
6. 既存の制約事項や禁止事項を弱めない。
7. 評価に合格するためだけの不適切な仕様変更を行わない。
8. 評価基準やテストケースを、評価結果を良くする目的で変更しない。
9. 改善前の内容をGitで追跡できる状態にする。
10. ユーザーの明示的な許可なく、保護対象ファイルや機密情報を変更しない。
11. 改善候補と正式版を明確に区別する。
12. 許可された成果物の出力先以外にファイルを作成しない。
13. 既存の未コミット変更を上書き・破棄しない。

## 6. 改善手順

### STEP 1. 振り返りレポートの読み込み

指定されたKPTファイルを読み込む。

以下の項目を取得する。

- 実行スキル
- 実行概要
- Keep
- Problem
- Try
- 改善対象
- 改善理由
- 関連する評価結果

内容が不足している場合は、関連する実行ログや評価レポートを参照する。

### STEP 2. 改善対象の特定

KPTの内容から改善対象を特定する。

対象の優先順位は以下とする。

1. 明確な不具合や品質問題の再発防止
2. eval-skill で FAIL となった問題の解消
3. 業務スキルの手順や判断基準の明確化
4. 作業効率や再現性の改善
5. その他の軽微な改善

複数のProblemがある場合は、それぞれ独立した改善項目として扱う。

### STEP 3. Tryの妥当性評価

各Tryについて以下を確認する。

| ID | チェック項目 | PASS条件 |
|---|---|---|
| T1 | Problemとの関連性 | 対応するProblemが明確である |
| T2 | 改善効果 | Problemの解消につながる |
| T3 | 実現可能性 | 対象スキルの定義で実現できる |
| T4 | 副作用 | 既存の正常な動作を損なわない |
| T5 | 適用範囲 | 他の類似タスクにも適用できる |
| T6 | 安全性 | セキュリティや権限上の問題がない |

判定ルール：

- すべてPASSの場合、改善候補として採用する。
- 1つでもFAILの場合、そのTryは採用しない。
- 根拠が不足している場合は保留する。
- 採用しなかったTryについては、その理由を記録する。

Tryの内容が不適切な場合、Problemを解消できる別の改善案を作成してよい。

ただし、元のProblemを解決できない改善案は採用しない。

### STEP 4. 改善前の状態を確認

変更前に以下を確認する。

- 対象スキルの現在の内容
- Gitの作業ツリーの状態
- 現在のブランチ
- 対象スキルに関連するテストケース
- 過去の評価レポート
- 関連する評価基準

既存の未コミット変更がある場合は、その内容を確認する。

他の作業による変更を上書きしたり、破棄したりしない。

対象スキルの変更前の内容を保持する。

### STEP 5. 改善候補の作成

改善後の SKILL.md を以下の場所に作成する。

```text
skill-development/proposals/<skill-name>/<run-id>/SKILL.md
```

重要：

このSTEPでは正式版の SKILL.md を変更してはならない。

変更時のルール：

1. 既存の目的と責務を維持する。
2. 既存の手順と矛盾する記述を追加しない。
3. 曖昧な指示は具体的な条件と動作に置き換える。
4. PASS / FAIL の判定条件を明文化する。
5. 入力不足時の動作を明文化する。
6. 禁止事項と制約事項を維持する。
7. 必要以上にスキルの構造を変更しない。
8. 改善と無関係な変更を加えない。

特に以下を優先して改善する。

- 判断条件の明確化
- 手順の具体化
- 入力と出力の明確化
- エラー処理の明確化
- 例外条件の明確化
- 再現性の向上

改善候補の作成後、ファイルが存在することを確認する。

### STEP 6. 変更差分の確認

正式版と改善候補を比較し、差分を確認する。

以下をチェックする。

| ID | チェック項目 | PASS条件 |
|---|---|---|
| D1 | 変更対象 | 許可された内容だけが変更されている |
| D2 | Problemへの対応 | 対象Problemを解消する変更になっている |
| D3 | 既存仕様 | 既存の正常な仕様が維持されている |
| D4 | 制約事項 | 既存の禁止事項が維持されている |
| D5 | 整合性 | SKILL.md 内に矛盾がない |
| D6 | 不要な変更 | 改善と無関係な変更がない |

1つでもFAILがある場合は改善候補を修正する。

修正後、再度差分を確認する。

### STEP 7. 品質ガード

改善候補に対して品質ガードを実施する。

#### 7.1 構文・形式チェック

- YAML Frontmatter が正しく記述されている。
- name がスキル名と一致している。
- description がスキルの目的を適切に説明している。
- Markdownの構造が正しい。
- 見出しと手順の順序が整合している。
- ファイル参照が正しい。

#### 7.2 内容チェック

- 入力条件が明確である。
- 実行手順が順序立てて定義されている。
- 判断条件が具体的である。
- 出力形式が明確である。
- 異常系の処理が定義されている。
- 禁止事項が明記されている。

#### 7.3 安全性チェック

- 不必要な権限昇格を要求していない。
- 機密情報を出力しない。
- 破壊的な操作を無条件に許可していない。
- ユーザーの承認が必要な操作を自動実行しない。
- 外部システムへの操作範囲が明確である。

品質ガードの結果はSTEP 8の評価レポートに記録する。

### STEP 8. eval-skill による再評価

品質ガード完了後、eval-skill を実行する。

評価対象は必ずSTEP 5で作成した改善候補とする。

評価条件：

1. 改善前と同じテストケースを使用する。
2. 旧版と新版の差分を比較する。
3. 再現性・改善度・副作用の3軸で評価する。
4. 評価レポートを保存する。
5. 総合評価を取得する。

評価レポートの保存先：

```text
skill-development/evaluations/<skill-name>/<run-id>/evaluation.md
```

評価レポートには以下を記録する。

- 評価対象のスキル名
- 改善前の SKILL.md のパス
- 改善候補の SKILL.md のパス
- 使用したテストケース
- 品質ガードの結果
- 再現性の評価
- 改善度の評価
- 副作用の評価
- 総合評価
- FAIL項目とその理由
- 最終判定

判定ルール：

| 評価結果 | 対応 |
|---|---|
| PASS | STEP 9に進む |
| FAIL | 問題を分析し、改善案を再検討する |
| NOT EVALUATED | 不足情報を確認し、評価できる状態にする |

FAILの場合：

- FAILとなった項目を特定する。
- 原因を確認する。
- 修正可能な場合は改善候補を修正する。
- 同じテストケースで再評価する。
- 評価レポートを更新する。

再評価を繰り返してもPASSにならない場合は、自動的に処理を継続しない。

再試行は最大3回とする。

3回以内にPASSにならない場合は、改善処理を停止してユーザーに報告する。

評価基準やテストケースを変更してPASSにすることは禁止する。

### STEP 9. 正式版への反映

eval-skill の総合評価がPASSの場合のみ実行する。

正式版の保存先は、STEP 4で確認した対象スキルの元のパスとする。

例：

```text
正式版:
.agents/skills/<skill-name>/SKILL.md

改善候補:
skill-development/proposals/<skill-name>/<run-id>/SKILL.md
```

反映手順：

1. 正式版の現在の内容を再確認する。
2. 改善候補と正式版の差分を再確認する。
3. 評価対象と反映対象が同一であることを確認する。
4. 正式版への反映が許可されていることを確認する。
5. 改善候補の内容を正式版へ反映する。
6. 正式版の内容と改善候補の内容が一致していることを確認する。

注意事項：

- 評価PASS前に正式版を変更しない。
- 正式版に他の変更が加わっている場合は上書きしない。
- 正式版への書き込み権限がない場合は処理を停止する。
- Sandbox の制限を無断で回避しない。
- 書き込みに失敗した場合、正式版への反映が完了したと報告しない。

正式版への反映に失敗した場合は、改善候補を保持し、理由を改善レポートに記録する。

### STEP 10. Pull Requestの作成

正式版への反映が完了し、品質ガードと eval-skill の評価がPASSの場合、Pull Requestを作成する。

PR作成前に以下を確認する。

- 対象リポジトリ
- ベースブランチ
- 作業ブランチ
- 変更対象ファイル
- Gitの差分
- 品質ガード結果
- eval-skill の評価レポート
- 改善候補と正式版の一致

ブランチ名は以下の形式を推奨する。

`improve/<skill-name>/<run-id>`

PRタイトルは以下の形式とする。

`[skill-improvement] <skill-name>: <改善内容>`

PR本文には以下を必ず記載する。

#### PR本文の構成

##### 1. 改善の背景

- 元のProblem
- 発生した問題

##### 2. 改善内容

- 変更したファイル
- 変更した手順
- 変更理由

##### 3. KPTとの対応

- 対応するKeep
- 対応するProblem
- 対応するTry

##### 4. 品質検証

- 品質ガード結果
- eval-skill の総合評価
- 各評価軸の結果
- 評価レポートへのリンク

##### 5. 成果物

- 改善候補のパス
- 評価レポートのパス
- 改善レポートのパス

##### 6. リスク

- 想定される副作用
- 未解決事項
- 追加確認が必要な項目

PR作成後、PR番号とURLを記録する。

PRを作成できない場合は、変更差分と作成できなかった理由を報告する。

PR作成に失敗した場合でも、作成済みの成果物は削除しない。

## 7. マージ判定

自動マージは、明示的に許可された場合に限り実施する。

### 7.1 自動マージの必須条件

以下の条件をすべて満たす必要がある。

| ID | 条件 | 必須 |
|---|---|---|
| M1 | eval-skill の総合評価がPASS | 必須 |
| M2 | 品質ガードがすべてPASS | 必須 |
| M3 | CIがすべて成功している | 必須 |
| M4 | 未解決のレビュー指摘がない | 必須 |
| M5 | 競合が存在しない | 必須 |
| M6 | 明示的な自動マージ許可がある | 必須 |
| M7 | 保護対象ファイルの変更がない | 必須 |

### 7.2 自動マージを禁止する変更

以下に該当する場合は、評価結果にかかわらず自動マージしない。

- 権限やアクセス制御の変更
- セキュリティポリシーの変更
- 秘密情報や認証情報に関係する変更
- 破壊的操作の許可範囲の変更
- ユーザー承認を省略する変更
- 評価基準や品質ガード自体の変更
- リポジトリの保護設定に関する変更

### 7.3 自動マージの判定

| 条件 | 判定 |
|---|---|
| すべての必須条件を満たす | 自動マージ可能 |
| 1つでもFAILがある | マージ禁止 |
| 1つでも未確認項目がある | マージ禁止 |
| 自動マージ許可がない | マージ禁止 |
| 保護対象の変更がある | 人間のレビュー必須 |

自動マージを許可する設定がない場合は、PRを作成してレビュー待ちとする。

PRの作成とマージは別の操作として扱う。

### 7.4 マージ後の確認

マージを実行した場合は、実行結果を確認する。

- PRがマージ済みになっている。
- 対象ブランチに変更が反映されている。
- マージ結果にエラーがない。

マージ結果を確認できない場合は、成功と報告しない。

```markdown
## 9. 最終結果

- 処理結果: SUCCESS / PARTIAL / FAILED
- 停止したSTEP:
- 備考:
```

### 8.1 処理結果の定義

| 結果 | 条件 |
|---|---|
| SUCCESS | 正式版への反映とPR作成が完了した |
| PARTIAL | 改善候補と評価レポートは作成できたが、正式版への反映またはPR作成が未完了 |
| FAILED | 改善処理を完了できず、必要な成果物も作成できなかった |

PRが未マージの場合でも、PR作成まで正常に完了していればSUCCESSとしてよい。

ただし、マージ状態は別途明記する。

改善レポートを作成した後、ファイルが存在することを確認する。

## 9. 処理の停止条件

以下の場合は処理を停止する。

- 対象スキルを特定できない。
- 振り返りレポートを取得できない。
- 改善対象の根拠が不足している。
- 既存変更との競合が発生した。
- 品質ガードに合格しない。
- eval-skill の評価が3回以内にPASSにならない。
- 成果物の保存に失敗した。
- 正式版への反映に必要な権限がない。
- PR作成に必要な権限がない。
- 安全性に関する問題を検出した。

停止した場合は以下を報告する。

- 停止したSTEP
- 停止理由
- 発生した問題
- 必要な対応
- 現在のファイルやブランチの状態
- 作成済み成果物の保存先

作成済みの変更や成果物、PRを許可なく削除・破棄しない。

## 10. 完了報告

処理終了後、呼び出し元に以下を返す。

- 改善対象スキル
- 変更したファイル
- 改善内容
- 対応したProblemとTry
- 品質ガード結果
- eval-skill の評価結果
- 改善候補の保存先
- 評価レポートの保存先
- 改善レポートの保存先
- 正式版の保存先
- PR番号とURL
- マージ結果
- 未解決事項

特に、以下の3つのパスは必ず報告する。

1. 改善候補: `proposals/`
2. 評価レポート: `evaluations/`
3. 改善レポート: `reports/`

マージしていない場合は、その理由を明記する。

## 11. 最終ルール

- 改善の根拠はKPTと関連資料に求める。
- Tryを無条件に実装しない。
- 対象外のスキルやファイルを変更しない。
- 評価基準を変更して評価を通過させない。
- 改善候補は必ず専用ディレクトリに保存する。
- 評価合格前に正式版を変更しない。
- 評価レポートと改善レポートを必ず保存する。
- 成果物の保存先を勝手に変更しない。
- 品質検証前にPRを完成扱いにしない。
- eval-skill のPASSを独立した品質保証とみなさない。
- 明示的な許可なしに自動マージしない。
- 操作結果を確認せず、成功と報告しない。
