# retro

## 1. 目的

業務スキルの実行結果を振り返り、今後のスキル改善に利用できる情報を記録する。

本スキルの責務は以下の3つとする。

1. 業務スキルの実行結果を分析する。
2. Keep / Problem / Try（KPT）を抽出して記録する。
3. 改善が必要な場合、改善情報を improve-skill に引き渡す。

本スキル自身は業務スキルの実装や修正を行わない。

## 2. トリガー

以下の条件を満たした場合に実行する。

- bugfix、refactor などの業務スキルが正常に完了した。
- 呼び出し元の業務スキルから明示的に本スキルが呼び出された。

### 実行対象外

以下の場合は通常の振り返りを実行しない。

- 業務スキルが実行途中で終了した。
- 業務スキルが失敗し、完了条件を満たしていない。
- ユーザーが作業の中止を要求した。
- 業務スキルの実行結果が存在しない。

ただし、失敗した作業についてユーザーまたは呼び出し元が明示的に振り返りを要求した場合は実行してよい。

## 3. 入力

以下の情報を呼び出し元から受け取る。

| 入力 | 必須 | 説明 |
|---|---|---|
| 業務スキル名 | 必須 | 実行したスキル名 |
| 実行結果 | 必須 | 実施内容、変更内容、実行結果 |
| 実行ログ | 推奨 | コマンド出力、操作履歴、エラーなど |
| ドライラン評価レポート | 任意 | eval-skill が生成した評価レポート |
| 改善前の問題 | 任意 | 作業開始時に確認されていた問題 |

### 入力の取得ルール

1. 呼び出し元から渡された情報を最優先する。
2. 不足情報は、実行ログや関連ファイルから取得する。
3. ログの場所が不明な場合は、プロジェクト内の関連するログを検索する。
4. 存在しないログや評価レポートを推測で作成しない。
5. 取得できなかった情報は「未取得」と記録する。
6. 同一タスクに関係しないログを混在させない。

ドライラン評価レポートが存在しない場合も、実行ログをもとにKPTを作成してよい。

## 4. 振り返り手順

### STEP 1. 実行内容の確認

以下を確認する。

- 実行した業務スキル
- 作業の目的
- 実施した作業
- 変更したファイル
- 実行したテスト
- テスト結果
- 発生したエラーや問題
- 最終的な完了状態

確認できた事実と推測を区別する。

### STEP 2. 関連資料の確認

以下の資料を確認する。

1. 業務スキルの実行ログ
2. ドライラン評価レポート（存在する場合）
3. 業務スキルが生成した成果物
4. 作業開始時の問題や要求事項

複数の資料で情報が矛盾する場合は、実際の実行結果を優先し、矛盾した内容も記録する。

### STEP 3. KPTの抽出

実行結果からKeep / Problem / Tryを抽出する。

#### 3.1 Keep（継続すること）

今後も維持すべき有効な手順、設計、判断、仕組みを記録する。

抽出条件：

- 期待した結果が得られた。
- 作業効率や品質の向上につながった。
- 問題の予防や早期発見に役立った。
- 他の類似タスクにも適用できる。

記録例：

- 変更前後のテストを実施したことで、既存機能への影響を検出できた。
- 修正対象を限定したことで、不要なファイル変更を防止できた。

単に実施しただけで効果が確認できない作業はKeepに含めない。

#### 3.2 Problem（問題点）

作業中に発生した問題、非効率な手順、判断の誤り、不足していた情報を記録する。

抽出条件：

- 期待した結果が得られなかった。
- 作業に余計な時間や手戻りが発生した。
- 手順や仕様が曖昧だった。
- テストや確認が不足していた。
- スキルの指示と実際の動作に不一致があった。
- 評価レポートでFAILとなった項目が存在した。

記録例：

- 入力条件の定義が不足していたため、処理対象の判断に手戻りが発生した。
- エラー処理の確認が不足しており、異常系のテストが追加で必要になった。

問題が発生しなかった場合は「顕著な問題なし」と記録する。

#### 3.3 Try（次回試すこと）

Problemを解消するために、次回以降に実施する具体的な改善策を記録する。

抽出条件：

- Problemを解消できる。
- 実行可能な具体的な行動である。
- 改善対象と改善内容が明確である。
- 類似タスクで再利用できる。

記録例：

- 入力条件と異常系の処理を業務スキルに明記する。
- 修正後のテストケースに境界値の検証を追加する。
- 実行前に変更対象ファイルの一覧を確認する。

Tryは可能な限りProblemと対応付ける。

Problemが存在しない場合でも、効果が確認された改善案があればTryとして記録してよい。

### STEP 4. KPTの品質確認

抽出したKPTについて、以下を確認する。

| ID | チェック項目 | PASS条件 |
|---|---|---|
| K1 | 事実との整合性 | 実行結果やログに根拠がある |
| K2 | 分類の適切性 | Keep / Problem / Tryの定義に合致する |
| K3 | 具体性 | 内容が具体的で理解できる |
| K4 | 重複の排除 | 同じ内容が複数項目に重複していない |
| K5 | 改善可能性 | Tryが実行可能な改善行動になっている |

判定ルール：

- すべてPASSの場合、KPTを確定する。
- FAILがある場合、該当項目を修正して再確認する。
- 根拠のない内容は削除するか「仮説」と明記する。

### STEP 5. KPTファイルの作成

振り返り結果を以下の場所に保存する。

`docs/retrospectives/retro_YYYYMMDD_HHMMSS.md`

作成ルール：

- Markdown形式で作成する。
- ディレクトリが存在しない場合は作成する。
- ファイル名の日時は作成時のローカル時刻を使用する。
- 既存ファイルを上書きしない。
- 実行内容とKPTを対応付ける。
- 根拠のない内容を記載しない。

## 5. improve-skill との連携

KPTファイルの保存後、Tryの内容を確認する。

### 呼び出し条件

以下のいずれかに該当する場合、improve-skill を呼び出す。

- 業務スキルの手順や定義に改善が必要である。
- Problemの再発防止にスキルの変更が必要である。
- eval-skill の評価結果にFAILが存在する。
- 呼び出し元から改善プロセスへの引き継ぎを明示的に要求されている。

以下の場合は呼び出さない。

- 改善対象が存在しない。
- Tryが業務スキルの変更を必要としない単発の作業上の注意事項だけである。
- 必要な情報が不足しており、改善対象を特定できない。

### 呼び出し方法

Codexで利用可能な improve-skill を明示的に指定して呼び出す。

呼び出し時には、以下の情報を渡す。

1. 改善対象のスキル名とファイルパス
2. KPTファイルのパス
3. 改善対象のProblem
4. 対応するTry
5. ドライラン評価レポートのパス（存在する場合）

### 連携ルール

- KPTの内容を勝手に変更して渡さない。
- ProblemとTryの対応関係を維持する。
- 改善対象と無関係なスキルを変更しない。
- improve-skill に評価結果を引き渡すだけとし、retro自身でスキルを修正しない。
- improve-skill が呼び出せない場合は、その理由を記録して終了する。

## 6. 最終確認

処理終了前に以下を確認する。

| ID | チェック項目 | PASS条件 |
|---|---|---|
| F1 | 実行内容の記録 | 実行概要が記録されている |
| F2 | KPTの作成 | Keep / Problem / Tryが分類されている |
| F3 | 根拠の記録 | 各項目に根拠がある、または仮説と明記されている |
| F4 | ファイル保存 | 指定ディレクトリにファイルが存在する |
| F5 | 改善連携 | 呼び出し条件に従って連携またはスキップされている |

確認できなかった項目をPASSにしない。

## 7. 完了報告

処理完了後、呼び出し元に以下を返す。

- 作成したKPTファイルのパス
- Keepの件数
- Problemの件数
- Tryの件数
- improve-skill の呼び出し結果
- 未解決事項

## 8. 禁止事項

- 実行ログに存在しない事象を作らない。
- 成果が確認できない作業をKeepにしない。
- Problemを隠したり、過小評価したりしない。
- 実行していないテストを実施済みと記載しない。
- 根拠のないTryを追加しない。
- KPT作成のために業務スキルの成果物を変更しない。
- 振り返りの過程で業務スキルを勝手に修正しない。
- improve-skill の呼び出し結果を確認せず、呼び出し成功と報告しない。
