# orchestrator

## 1. 目的

業務スキルの実行から改善までの一連のワークフローを統括する。

本スキルは各処理を直接実行するのではなく、専門スキルを適切な順序で呼び出し、処理結果を管理する。

### 管理対象

| スキル | 責務 |
|---|---|
| 業務スキル | bugfix、refactor、featureなどの業務実行 |
| eval-skill | 品質評価とドライラン検証 |
| retro | Keep / Problem / Tryの抽出と記録 |
| improve-skill | スキルの改善案作成、修正、PR作成 |

本スキルはワークフローの進行管理だけを担当する。

各専門スキルの責務を代行しない。

## 2. トリガー

以下の場合に実行する。

- ユーザーが一連の業務実行と改善ワークフローを要求した。
- ユーザーが業務スキルの実行を本スキルに依頼した。
- 業務スキルから後続ワークフローの統括を明示的に依頼された。

### 実行対象外

- 単発の質問や説明だけを要求された場合
- ワークフローを必要としない単純なファイル変更
- ユーザーが振り返りや改善を明示的に拒否した場合

ユーザーの要求範囲を超えて、自動的に改善やPR作成を開始しない。

## 3. 入力

以下の情報を受け取る。

| 入力 | 必須 | 説明 |
|---|---|---|
| 業務スキル名 | 必須 | 実行対象のスキル |
| 業務内容 | 必須 | 実行するタスク |
| 評価の実施 | 必須 | 初回評価を行うか |
| 振り返りの実施 | 必須 | KPTを作成するか |
| 改善の実施 | 必須 | improve-skillを実行するか |
| PR作成許可 | 任意 | PR作成を許可するか |
| 自動マージ許可 | 任意 | 自動マージを許可するか |

明示されていない場合のデフォルト：

- 評価：実施する
- 振り返り：実施する
- 改善：実施する
- PR作成：許可されていない場合は作成しない
- 自動マージ：禁止

ただし、ユーザーが指定した実行範囲を優先する。

## 4. 基本ルール

以下を必ず守る。

1. 定義された実行順序を守る。
2. 各スキルを明示的に呼び出す。
3. 前段の処理が完了してから次の処理を開始する。
4. 各スキルの出力を次のスキルに引き渡す。
5. 同一タスクの成果物だけを引き継ぐ。
6. 処理結果を確認せずに次のSTEPへ進まない。
7. FAILやエラーが発生した場合は、後続処理の実行可否を判断する。
8. スキルの実行に失敗した場合、成功したものとして扱わない。
9. ユーザーの承認が必要な操作を勝手に実行しない。
10. 各スキルの責務を変更しない。

## 5. ワークフロー

### STEP 1. 実行計画の作成

入力された業務内容から、実行対象の業務スキルを特定する。

以下を確認する。

- 業務スキルが存在する。
- スキルの目的がタスクに適合している。
- 入力条件が満たされている。
- 実行に必要な権限がある。
- 後続ワークフローの実施条件が明確である。

対象スキルを特定できない場合は、推測で選択せずユーザーに確認する。

確認後、以下の実行計画を作成する。

| 順序 | 処理 | 実行条件 |
|---|---|---|
| 1 | 業務スキル | 必須 |
| 2 | eval-skill | 評価が有効な場合 |
| 3 | retro | 振り返りが有効な場合 |
| 4 | improve-skill | 改善が有効かつ改善対象がある場合 |
| 5 | eval-skill | スキル変更が発生した場合 |
| 6 | 最終確認 | 必須 |

### STEP 2. 業務スキルの実行

指定された業務スキルを明示的に呼び出す。

実行結果から以下を取得する。

- 実行したスキル名
- 実施内容
- 変更したファイル
- 実行ログ
- テスト結果
- エラー情報
- 完了状態

業務スキルが正常に完了した場合のみ、次のSTEPへ進む。

#### 判定

| 結果 | 動作 |
|---|---|
| PASS | 次のSTEPへ進む |
| FAIL | ワークフローを停止する |
| NOT COMPLETED | ワークフローを停止する |

停止時は実行結果と原因をユーザーに報告する。

### STEP 3. 初回評価

評価が有効な場合、eval-skillを明示的に呼び出す。

入力として以下を渡す。

- 業務スキル名
- 業務スキルの実行結果
- 実行ログ
- テスト結果
- 評価対象の成果物
- 必要な評価条件

評価レポートを取得し、以下を確認する。

- 再現性
- 改善度
- 副作用
- 総合評価

評価結果を後続処理に引き渡す。

#### 判定

| 総合評価 | 動作 |
|---|---|
| PASS | STEP 4へ進む |
| FAIL | 問題を記録し、STEP 4へ進む |
| NOT EVALUATED | 評価不能の理由を記録し、STEP 4へ進む |

初回評価のFAILは、振り返りによって改善対象を特定するための情報として扱う。

ただし、安全性に重大な問題がある場合は後続処理を停止する。

### STEP 4. 振り返り

振り返りが有効な場合、retroを明示的に呼び出す。

以下を入力として渡す。

- 業務スキル名
- 業務スキルの実行結果
- 実行ログ
- 初回評価レポート
- 変更したファイル
- 発生した問題

retroの完了後、KPTファイルが実際に作成されていることを確認する。

取得する情報：

- KPTファイルのパス
- Keepの件数
- Problemの件数
- Tryの件数
- 改善対象

KPTファイルが存在しない場合は、次のSTEPへ進まない。

### STEP 5. スキル改善

改善が有効な場合、improve-skillを明示的に呼び出す。

入力として以下を渡す。

- 対象スキル名
- 対象スキルのファイルパス
- KPTファイルのパス
- 初回評価レポート
- 改善対象
- PR作成許可
- 自動マージ許可

improve-skillの完了後、以下を確認する。

- 改善対象の変更内容
- 変更されたファイル
- 品質ガード結果
- PR作成結果
- PRのURL
- マージ状態

#### 判定

| 結果 | 動作 |
|---|---|
| 改善不要 | STEP 6へ進む |
| 改善成功 | STEP 6へ進む |
| 改善失敗 | 停止して報告 |
| 改善保留 | 停止して報告 |

改善対象が存在しない場合は、無理に変更を作成しない。

PR作成が許可されていない場合は、PR作成前の段階で停止し、変更内容を報告する。

### STEP 6. 改善後の再評価

対象スキルの変更が発生した場合、eval-skillを再度呼び出す。

初回評価と同じテストケースを使用する。

入力として以下を渡す。

- 改善前のスキル定義
- 改善後のスキル定義
- 改善前の評価レポート
- KPTファイル
- 改善内容
- 既存のテストケース

評価軸は以下とする。

- 再現性
- 改善度
- 副作用

#### 判定

| 総合評価 | 動作 |
|---|---|
| PASS | STEP 7へ進む |
| FAIL | 改善未完了として記録 |
| NOT EVALUATED | 評価未完了として記録 |

FAILの場合、improve-skillに再検討を依頼できる。

ただし、再改善は最大3回までとする。

3回以内にPASSにならない場合は、自動改善を停止する。

評価基準やテストケースを変更してPASSにすることは禁止する。

### STEP 7. 最終確認

すべての処理が終了したら、以下を確認する。

| ID | 確認項目 | PASS条件 |
|---|---|---|
| F1 | 業務実行 | 業務スキルが完了している |
| F2 | 初回評価 | 評価結果が記録されている |
| F3 | 振り返り | KPTファイルが存在する |
| F4 | 改善 | 改善結果が記録されている |
| F5 | 再評価 | 改善後の評価結果が記録されている |
| F6 | PR | 作成許可がある場合に結果が確認できる |
| F7 | マージ | 実施した場合に結果が確認できる |

実行対象外のSTEPはSKIPPEDとして記録する。

未実施のSTEPをPASSとして扱わない。

### STEP 8. 完了報告

ワークフロー全体の結果をユーザーに報告する。

以下を必ず含める。

- 実行した業務スキル
- 業務実行結果
- 初回評価結果
- KPTファイルのパス
- 改善対象と変更内容
- 改善後の評価結果
- PRのURL
- マージ結果
- 未解決事項
- ワークフローの最終状態

## 6. 状態管理

各STEPの実行状態を以下のいずれかで管理する。

| 状態 | 意味 |
|---|---|
| PENDING | 未実行 |
| RUNNING | 実行中 |
| PASS | 正常完了 |
| FAIL | 実行失敗または評価不合格 |
| SKIPPED | 実行条件に該当せずスキップ |
| BLOCKED | 前提条件不足などにより実行不能 |

各STEPの結果を確認するまで、状態を更新しない。

### 状態遷移のルール

- PENDINGからRUNNINGへ変更する。
- RUNNINGからPASS、FAIL、SKIPPED、BLOCKEDのいずれかへ変更する。
- FAILとBLOCKEDは、原因を解消するまで後続STEPを開始しない。
- SKIPPEDは実行条件を満たさない場合にのみ使用する。
- 完了していない処理をPASSに変更しない。

## 7. エラー処理

以下の場合はワークフローを停止する。

- 呼び出し対象のスキルが存在しない。
- スキルの実行結果を取得できない。
- 必須ファイルが存在しない。
- ファイルの内容が不正である。
- 前段の処理が失敗した。
- 必要な権限がない。
- 予期しないファイル変更が発生した。
- 安全性に問題がある。

エラー発生時は以下を記録する。

- 発生したSTEP
- エラー内容
- 発生原因
- 実行済みのSTEP
- 未実行のSTEP
- 現在の作業状態
- 再開に必要な対応

原因を特定できない場合は、推測で処理を続けない。

## 8. 再実行ルール

途中で停止した場合、再実行時には既存の成果物と状態を確認する。

以下を守る。

1. 完了済みSTEPを無条件に再実行しない。
2. 既存のKPTファイルを重複作成しない。
3. 既存のPRを重複作成しない。
4. 前回の実行結果と今回の実行結果を混在させない。
5. 前回の状態を確認できない場合は、再実行前に確認する。

再開時は、失敗または未実行のSTEPから開始する。

ただし、前段の成果物が変更されている場合は、影響するSTEPを再実行する。

## 9. 実行履歴

ワークフローの実行結果を以下に記録する。

`docs/workflow-reports/workflow_YYYYMMDD_HHMMSS.md`

ディレクトリが存在しない場合は作成する。

ファイル名の日時は作成時のローカル時刻とする。

## 10. 禁止事項

- 各スキルを実行せずに実行済みと報告しない。
- 実行結果を確認せずに次のSTEPへ進まない。
- 前段の失敗を無視して後続処理を実行しない。
- 異なるタスクの成果物を混在させない。
- 各スキルの責務を勝手に変更しない。
- 評価基準を変更してPASSにしない。
- ユーザーの許可なくPRをマージしない。
- 既存の作業内容を勝手に破棄しない。
- 未確認の操作結果を成功と報告しない。
