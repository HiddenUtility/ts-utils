# Init Harness

ユーザーとの対話を通じて AI エージェントの運用要件を収集し、プロジェクトに適した AI エージェントハーネスを設計・構築する。

単にスキルファイルを作成するのではなく、AI エージェントが安定して作業し、その結果を評価し、継続的に改善できる仕組みを構築する。

## 1. 目的

本スキルの最終成果物は、プロジェクトに統合された AI エージェントハーネスである。

ハーネスは以下の機能を持つ。

1. AI エージェントの作業を制御する。
2. 作業内容に応じて適切なスキルを選択する。
3. スキルの実行結果を評価する。
4. 作業結果を振り返る。
5. 発見した問題を記録する。
6. 評価結果に基づいてスキルを改善する。
7. 改善後のスキルを再評価する。
8. 品質の低下を検出する。
9. 作業履歴と改善履歴を保存する。

## 2. 基本設計原則

### 2.1. 小規模モデルへの最適化

パラメータ数の少ないモデルでも安定して動作するように設計する。

以下を守る。

- 各スキルの責務を1つに限定する。
- スキルの入力と出力を明示する。
- 実行条件を明示する。
- 処理手順を番号付きで記述する。
- 判断条件を具体的に記述する。
- 例外処理を明示する。
- 暗黙の前提に依存しない。
- 複数のスキルに同じ責務を持たせない。
- 必要以上に長いコンテキストを渡さない。
- 作業状態をファイルなどの永続的な形式で管理する。

### 2.2. 自動化

ユーザーが指定した範囲内で、ハーネスの実行と改善を自動化する。

ただし、自動化の範囲はユーザーが決定した権限設定に従う。

### 2.3. 再現性

同じ入力と同じ条件であれば、可能な限り同じ手順で評価できるようにする。

- 評価条件を記録する。
- 評価ケースを保存する。
- 実行結果を保存する。
- 改善前後の結果を比較する。
- 評価に使用したスキルのバージョンを記録する。

### 2.4. 検証可能性

ハーネスの構成要素は、実際に動作することを確認できなければならない。

ファイルを作成しただけで構築完了としてはいけない。

# Phase 1: 要件ヒアリング

## 4. ヒアリング方針

ユーザーとの会話を通じて、ハーネスの要件を収集する。

### 4.1. 質問ルール

1. 一度に大量の質問を提示しない。
2. 原則として1回の発言で1つのテーマを扱う。
3. 既に回答された内容は再質問しない。
4. 技術的な選択肢にはメリットとデメリットを示す。
5. 判断を委任された場合は推奨案を提示する。
6. 未決定事項を決定済みとして扱わない。
7. ユーザーが指定していない自動化を追加しない。
8. プロジェクトに不要な機能は省略する。

## 5. ヒアリング項目

### 5.1. 実行環境

以下を確認する。

- AI エージェント
- AI モデル
- エージェントの実行環境
- スキル定義形式
- スキルの配置場所
- ローカル実行かクラウド実行か
- 利用可能な外部ツール
- ファイル操作権限
- Git 操作権限
- ネットワークアクセスの制約

### 5.2. ハーネスの目的

- どのような作業を自動化するか
- 対象となるプロジェクト
- エージェントの担当範囲
- 人間が担当する範囲
- 自動化の最終目標
- 将来的な拡張方針

### 5.3. スキル管理

- 必要なスキルの種類
- スキルの分割方針
- スキル間の依存関係
- スキルの呼び出し方法
- スキルの実行順序
- スキルの入力・出力形式
- スキルのバージョン管理
- スキルの追加・削除方法

### 5.4. オーケストレーション

- メインとなるオーケストレーターの有無
- タスクの分割方法
- スキルの選択方法
- 実行順序の制御
- 実行失敗時の処理
- 再試行の方針
- 最大実行回数
- 実行終了条件
- 並列実行の有無
- 人間へのエスカレーション条件

### 5.5. 評価システム

- 評価対象
- 評価基準
- 評価ケースの管理方法
- 正解データの有無
- 評価方法
- 合格条件
- 回帰テストの方法
- 評価結果の保存先
- 評価頻度

### 5.6. 振り返りシステム

- 振り返りを実行するタイミング
- 振り返りの対象
- 問題の分類方法
- 改善案の作成方法
- 改善案の優先順位
- 振り返り結果の保存先

### 5.7. 自己改善システム

- 自動改善の対象
- 改善可能なスキル
- 改善案の評価方法
- 改善前後の比較方法
- 改善の採用条件
- 改善の取り消し方法
- 人間の承認が必要な条件

### 5.8. 状態管理・ログ

- 実行履歴
- スキル実行履歴
- 評価結果
- 改善履歴
- エラーログ
- 中断時の復旧
- データの保存形式
- 保存期間

### 5.9. 品質・安全性

- 実行可能な操作
- 禁止操作
- ファイル変更の制限
- Git 操作の制限
- 外部通信の制限
- 秘密情報の取り扱い
- 自動マージの条件
- ロールバック方針

### 5.10. CI/CD・イベント連携

- GitHub Actions などの CI
- Pull Request との連携
- Git イベントとの連携
- スケジュール実行
- Hook / Event の利用
- 自動評価の実行条件
- 自動改善の実行条件

## 6. ヒアリング終了条件

以下が明確になったらヒアリングを終了する。

- [ ] 実行環境
- [ ] ハーネスの目的
- [ ] スキル管理方式
- [ ] オーケストレーション方式
- [ ] 評価方式
- [ ] 振り返り方式
- [ ] 自己改善方式
- [ ] 状態管理方式
- [ ] 品質・安全性
- [ ] 自動化・CI/CD

不要な機能は対象外としてよい。

# Phase 2: 全体設計

## 7. アーキテクチャ設計

ヒアリングした要件からハーネスの全体構成を設計する。

最低限、以下の構成要素を検討する。

| コンポーネント | 責務 |
|---|---|
| Orchestrator | タスクの受付・分解・実行制御 |
| Skills | 個別作業の実行 |
| Evaluator | スキルの品質評価 |
| Retrospective | 実行結果の振り返り |
| Improver | スキルの改善 |
| State Manager | 実行状態の管理 |
| Logger | 実行履歴の記録 |
| CI | 自動検証 |

すべてを必須にする必要はない。

要件に存在しない機能は追加しない。

## 8. コンポーネント間の連携

各コンポーネントの責務と入出力を明確にする。

以下を定義する。

- 呼び出し元
- 呼び出し先
- 入力データ
- 出力データ
- 実行条件
- エラー時の処理
- 状態の保存先

### 8.1. 標準的な処理フロー

基本的な自己改善サイクルは以下とする。

1. Orchestrator がタスクを受け取る。
2. Orchestrator が適切なスキルを選択する。
3. 対象スキルを実行する。
4. 実行結果を保存する。
5. Evaluator が実行結果を評価する。
6. Retrospective が問題点を整理する。
7. Improver が改善案を作成する。
8. 改善後のスキルを再評価する。
9. 合格条件を満たした場合のみ改善を採用する。
10. 実行結果と改善履歴を保存する。

実際の連携はユーザーが決定した要件に合わせる。

## 9. データ設計

ハーネスが管理するデータを定義する。

候補：

- タスク定義
- 実行状態
- 実行ログ
- 評価ケース
- 評価結果
- 振り返り結果
- 改善提案
- スキルの変更履歴

各データについて以下を決める。

- 保存形式
- 保存場所
- 必須項目
- 更新条件
- 保持期間

不要なデータベースや外部サービスを導入しない。

# Phase 3: スキル設計

## 10. スキル一覧

必要なスキルを洗い出し、一覧表を作成する。

| スキル | 責務 | 入力 | 出力 |
|---|---|---|---|
| orchestrator | タスク実行制御 | タスク | 実行結果 |
| eval-skill | スキル評価 | スキル・評価ケース | 評価結果 |
| retro | 振り返り | 実行結果 | 問題・改善案 |
| improve-skill | スキル改善 | 改善案 | 改善済みスキル |

上記は標準的な候補である。

ユーザーの要件に応じて追加・削除する。

## 11. スキル仕様

各スキルについて以下を定義する。

1. スキル名
2. 目的
3. 責務
4. 実行条件
5. 入力
6. 出力
7. 処理手順
8. エラー処理
9. 禁止事項
10. 完了条件

### 11.1. 責務の分離

- Orchestrator は個別作業の詳細な実装を担当しない。
- Evaluator は評価結果の判定を担当する。
- Retrospective は問題の分析と改善案の作成を担当する。
- Improver は承認された改善方針に基づいてスキルを変更する。

各スキルの責務を重複させない。

### 11.2. スキル間の依存関係

依存関係を明示する。

循環依存を作らない。

スキルの実行に必要な情報は、入力として明示的に渡す。

他のスキルが暗黙的に生成した情報を前提にしない。

# Phase 4: 実装

## 12. 実装方針

設計したハーネスを実際のリポジトリに構築する。

### 12.1. 実装順序

以下の順序を基本とする。

1. ディレクトリ構成を作成する。
2. 共通設定を作成する。
3. 状態管理・ログ管理を作成する。
4. 個別スキルを作成する。
5. Orchestrator を作成する。
6. スキル間の連携を定義する。
7. 評価ケースを作成する。
8. CI・自動化設定を作成する。
9. ドキュメントを作成する。

実装順序は依存関係に応じて変更してよい。

### 12.2. スキルの配置

Codex の場合、原則として以下に配置する。

```text
.agents/
└── skills/
    └── <skill-name>/
        └── SKILL.md
```

各スキルは独立したディレクトリを持つ。

### 12.3. スキルの記述

各 SKILL.md には YAML frontmatter を定義する。

必須項目：

- name
- description

description には、スキルの目的と使用条件を記述する。

本文には、実行手順・入力・出力・制約・完了条件を記載する。

### 12.4. 実装上の制約

- ユーザーが決定していない外部サービスを導入しない。
- 不要なスクリプトを作成しない。
- 同じ処理を複数箇所に重複実装しない。
- スキルの責務を混在させない。
- 既存の設定を無断で破壊しない。
- 実際に動作しない機能を完成済みとして扱わない。

# Phase 5: 動作検証

## 13. 検証方針

作成したハーネスが設計どおりに動作するか確認する。

ファイルの存在確認だけでは不十分である。

### 13.1. 構造検証

- [ ] 必要なディレクトリが存在する。
- [ ] 必要なスキルが存在する。
- [ ] 各 SKILL.md の frontmatter が正しい。
- [ ] スキル間の依存関係が正しい。
- [ ] 設定ファイルが正しい。
- [ ] ドキュメントと実装が一致している。

### 13.2. 機能検証

- [ ] Orchestrator がタスクを受け取れる。
- [ ] 適切なスキルを選択できる。
- [ ] スキルを指定された順序で実行できる。
- [ ] 実行結果が保存される。
- [ ] Evaluator が結果を評価できる。
- [ ] Retrospective が問題を整理できる。
- [ ] Improver が改善案を作成できる。
- [ ] 改善後の評価を実行できる。
- [ ] 失敗時に適切に停止できる。

実際に利用する実行方式で確認する。

Codex のスキル呼び出しが手動操作を必要とする場合、未検証の自動実行を実現済みと報告してはいけない。

### 13.3. 安全性検証

- [ ] 禁止操作が定義されている。
- [ ] 自動変更の対象範囲が明確である。
- [ ] 改善前の状態を復元できる。
- [ ] 評価に失敗した改善を採用しない。
- [ ] 秘密情報をログに記録しない。
- [ ] 人間の承認が必要な操作が明確である。

### 13.4. 不合格時の対応

検証に失敗した場合は原因を調査する。

修正可能な問題は修正し、再検証する。

環境上の制約で検証できない場合は、その理由と未検証の項目を明示する。

# Phase 6: ドキュメント作成

## 14. README.md

人間がハーネスの全体像を理解し、利用・保守できる README.md を作成する。

以下を基本項目とする。

1. ハーネスの目的
2. 全体アーキテクチャ
3. ディレクトリ構成
4. 各スキルの役割
5. スキル間の連携
6. 実行方法
7. 評価方法
8. 振り返り方法
9. 自己改善方法
10. ログと履歴の確認方法
11. CI・自動化
12. トラブルシューティング
13. 拡張方法

### 14.1. 図解

スキル間の連携は Mermaid で図解する。

図には以下を含める。

- 実行の起点
- 各スキル
- データの流れ
- 評価の流れ
- 改善の流れ
- 繰り返し処理

実際の実装と一致する図を作成する。

未実装の機能を実装済みとして図示しない。

# 17. 開始

このスキルが実行されたら、Phase 1 から開始する。

最初に以下を質問する。

「どのような AI エージェントハーネスを構築したいですか？ 使用するエージェント、モデル、ハーネスによって自動化したい作業、最終的な完成イメージを教えてください。」

回答に応じてヒアリングを進める。

最初から全体設計やファイル作成を開始してはいけない。
