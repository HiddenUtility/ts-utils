# Init Project

ユーザーとの対話を通じてプロジェクトの要件を収集し、Codex が正確に開発作業を実行できる `AGENTS.md` を作成する。

## 1. 基本方針

このスキルの最終成果物は、リポジトリルートの `AGENTS.md` である。

`AGENTS.md` は人間向けの説明資料ではなく、AI エージェントの行動を制御するための指示書として作成する。

特に、小規模なモデルでも誤解しにくい内容にする。

以下の原則を守る。

1. 曖昧な表現を使用しない。
2. 1つのルールには原則として1つの指示だけを書く。
3. 実行条件を明確にする。
4. 判断基準を明確にする。
5. 禁止事項を具体的に記述する。
6. 手順を実行順に記述する。
7. 例外条件を明示する。
8. ルール同士の矛盾をなくす。
9. 不要な説明と重複を減らす。
10. ユーザーが決定していない仕様を勝手に追加しない。

## 2. 実行フロー

以下の4つのフェーズを必ず順番に実行する。

| Phase | 内容 | 成果物 |
|---|---|---|
| 1 | 要件ヒアリング | プロジェクト要件 |
| 2 | 要件整理・確認 | 確定したプロジェクト仕様 |
| 3 | AGENTS.md 生成 | AGENTS.md |
| 4 | 自己検証 | 検証済み AGENTS.md |

各フェーズの終了条件を満たすまで、次のフェーズへ進まない。

# Phase 1: 要件ヒアリング

## 3. ヒアリングの進め方

ユーザーとの会話を通じて、プロジェクトの要件を収集する。

### 3.1. 質問ルール

1. 最初にプロジェクトの目的と完成イメージを質問する。
2. 一度に大量の質問を提示しない。
3. 原則として1回の発言で1つのテーマを扱う。
4. 独立した質問をまとめた方が回答しやすい場合は、複数質問してよい。
5. 回答済みの項目を再質問しない。
6. 曖昧な回答には具体例を示して確認する。
7. 技術的な選択肢には、簡潔なメリットとデメリットを付ける。
8. 技術選定を委任された場合は、推奨案と理由を提示する。
9. ユーザーが決定していない内容を決定済みとして扱わない。
10. プロジェクトに関係しない質問は省略する。

質問は、ユーザーが回答しやすい自然な会話形式にする。

質問票を一度にすべて提示してはいけない。

## 4. ヒアリング項目

以下の項目を確認する。

すべての項目を必ず質問する必要はない。回答やプロジェクトの性質に応じて必要な項目を選択する。

### 4.1. プロジェクト概要

- プロジェクト名
- プロジェクトの目的
- 解決したい問題
- 主な利用者
- 提供する機能
- 完成イメージ
- モノレポまたは単一プロジェクト
- 将来的な拡張方針

### 4.2. 技術スタック

- プログラミング言語
- 言語のバージョン
- フレームワーク
- ビルドツール
- パッケージ管理
- 対応 OS
- 対応プラットフォーム
- 外部ライブラリの利用方針

### 4.3. アーキテクチャ

- ディレクトリ構成
- モジュール・パッケージの分割方針
- コンポーネント間の依存関係
- 公開 API の設計方針
- エラー処理方針
- 設定管理方針
- データ管理方針
- セキュリティ方針

### 4.4. コーディング規約

- 命名規則
- フォーマット
- コメント・ドキュメントの言語
- 型の扱い
- エラー処理
- ログ出力
- 非同期処理
- パフォーマンス方針
- 禁止する実装パターン

### 4.5. テストと品質管理

- テストツール
- テストの種類
- テストの実行方法
- 静的解析ツール
- フォーマッター
- ビルドチェック
- 品質チェックの実行タイミング
- CI で実行するチェック

### 4.6. CI/CD と自動化

- CI/CD プラットフォーム
- CI の実行条件
- 自動テスト
- 自動リリースの有無
- デプロイの有無
- 自動化スクリプト
- AI エージェントの自動実行方針

### 4.7. Git 運用

- ブランチ戦略
- ブランチ命名規則
- コミットメッセージ規約
- Pull Request の作成ルール
- レビュー担当者
- マージ条件
- マージ方式
- AI エージェントに許可する Git 操作
- 人間による承認が必要な操作

### 4.8. AI エージェント運用

- 使用する AI エージェント
- AI エージェントの役割
- スキル定義形式
- スキルの配置場所
- スキル間の依存関係
- スキルの自動実行条件
- AI に許可する操作
- AI に禁止する操作
- 人間への確認が必要な条件
- 自動化する範囲
- AI による自己改善の方針

### 4.9. ドキュメント

- README の記載内容
- API ドキュメント
- 設計ドキュメント
- 開発者向けドキュメント
- ドキュメントの更新条件
- ドキュメントの言語

## 5. ヒアリング終了条件

次の項目が明確になったらヒアリングを終了する。

- [ ] プロジェクトの目的
- [ ] 技術スタック
- [ ] アーキテクチャの基本方針
- [ ] コーディング規約
- [ ] テストと品質管理
- [ ] CI/CD 方針
- [ ] Git 運用方針
- [ ] AI エージェントの権限と承認フロー
- [ ] ドキュメント方針

プロジェクトに不要な項目は対象外としてよい。

未決定事項が残る場合は、推奨案を提示してユーザーに確認する。

不明なままでも AGENTS.md の作成に影響しない事項は、無理に決定しない。

# Phase 2: 要件整理

## 6. 要件の整理

ヒアリング終了後、収集した情報を整理する。

次の形式でユーザーに提示する。

### Project Specification

| 項目 | 決定内容 |
|---|---|
| プロジェクト名 | |
| プロジェクトの目的 | |
| 技術スタック | |
| アーキテクチャ | |
| ディレクトリ構成 | |
| コーディング規約 | |
| テスト方針 | |
| CI/CD | |
| Git 運用 | |
| AI エージェント運用 | |
| ドキュメント方針 | |

### 未決定事項

決定していない項目を列挙する。

### 推奨事項

技術的な観点から推奨する設定があれば、理由とともに提示する。

### 矛盾チェック

以下を確認する。

- 技術スタックと開発規約が矛盾していないか。
- アーキテクチャとディレクトリ構成が整合しているか。
- Git 運用と AI の権限が矛盾していないか。
- CI のチェック内容とマージ条件が整合しているか。
- 自動化方針と承認フローが矛盾していないか。

## 7. ユーザー確認

整理した仕様をユーザーに提示し、確認を求める。

ユーザーから修正があれば仕様に反映する。

**ユーザーの確認を得る前に Phase 3 へ進んではいけない。**

# Phase 3: AGENTS.md 生成

## 8. 生成前の確認

AGENTS.md を作成する前に、リポジトリの状態を確認する。

確認対象：

- リポジトリのルート
- 既存の AGENTS.md
- 既存の README.md
- ディレクトリ構成
- Cargo.toml や package.json などのプロジェクト設定
- CI/CD 設定
- 既存の開発規約

実際のファイルとユーザーが決定した仕様に矛盾がある場合は、ユーザーに確認する。

既存の AGENTS.md がある場合は、無断で上書きしない。既存内容を確認し、ユーザーに更新方針を確認する。

## 9. AGENTS.md の構成

以下を基本構成とする。

必要な項目だけを採用する。

1. 基本ルール
2. プロジェクト概要
3. 技術スタック
4. リポジトリ構成
5. アーキテクチャ方針
6. コーディング規約
7. エラー処理方針
8. テスト方針
9. 品質ガード
10. CI/CD
11. Git 運用ルール
12. AI エージェント運用
13. スキル運用
14. ドキュメント方針
15. 禁止事項
16. 作業完了条件

## 10. 記述ルール

### 10.1. ルールの記述形式

各ルールには、必要に応じて以下を含める。

- 対象：どのファイル・作業・機能に適用するか。
- 指示：何を実行するか。
- 条件：いつ実行するか。
- 例外：実行しなくてもよい条件。
- 検証：どのように確認するか。

### 10.2. 曖昧な表現の禁止

次のような表現を避ける。

悪い例：

- テストを適切に実施する。
- 必要に応じてリファクタリングする。
- コードの品質を高める。
- なるべく安全に実装する。

良い例：

- Rust のソースコードを変更した場合、変更したクレートのテストを実行する。
- 最終確認では `cargo test --workspace` を実行する。
- テストに失敗した場合は原因を調査して修正する。
- テストを実行できない場合は理由を作業報告に記載する。

### 10.3. その他の記述ルール

- 1つの箇条書きには原則1つの指示を書く。
- 禁止事項には禁止する具体的な操作を書く。
- コマンドはコードブロックで記載する。
- 手順は番号付きリストで記載する。
- 条件分岐は「〜の場合」と明示する。
- ルールの優先順位を定義する。
- AI が自律的に判断してよい範囲を明確にする。
- 実際に使用するコマンドだけを記載する。
- 存在しないスクリプトや設定を前提にしない。
- 将来の予定と現在のルールを区別する。

### 10.4. 指示の優先順位

プロジェクト固有のルールと一般的な推奨事項を混同しない。

ユーザーが決定した仕様を優先し、一般的なベストプラクティスを独断で上書きしない。

# Phase 4: 自己検証

## 11. AGENTS.md の検証

生成した AGENTS.md を読み直し、以下のチェックリストで検証する。

### 11.1. 要件整合性

- [ ] ユーザーが決定した要件が反映されている。
- [ ] 指定されていない仕様を勝手に追加していない。
- [ ] 未決定事項を決定済みとして扱っていない。
- [ ] 要件同士に矛盾がない。
- [ ] 実際のプロジェクト構成と一致している。

### 11.2. 指示の明確性

- [ ] 曖昧な表現が残っていない。
- [ ] 各ルールの対象が明確である。
- [ ] 実行条件が明確である。
- [ ] 例外条件が明確である。
- [ ] 禁止事項が具体的である。
- [ ] 手順の順序が明確である。
- [ ] 作業完了条件が明確である。

### 11.3. 技術的整合性

- [ ] 記載したツールが技術スタックと一致している。
- [ ] 記載したコマンドが実行可能である。
- [ ] ディレクトリ構成が実際の構成と一致している。
- [ ] Git 運用ルールに矛盾がない。
- [ ] AI エージェントの権限が明確である。
- [ ] CI/CD の設定と整合している。

### 11.4. 修正

検証で問題が見つかった場合は修正する。

修正後、該当するチェックを再実行する。

## 12. 完了報告

検証が完了したら、以下をユーザーに報告する。

1. 作成したファイルのパス
2. 定義した主要なルール
3. 採用した技術的な方針
4. 未決定事項
5. 検証結果
6. 追加で整備するとよいファイルや設定

実施していない検証を実施済みとして報告しない。

---

# 13. 制約事項

以下を必ず守る。

- 最初の応答では AGENTS.md を作成しない。
- 最初の応答ではプロジェクトの目的と完成イメージを質問する。
- ヒアリングを省略して仕様を推測しない。
- 要件整理の確認前に AGENTS.md を作成しない。
- 既存ファイルを確認せずに上書きしない。
- ユーザーの既存作業を破壊しない。
- ユーザーが依頼していない追加設定ファイルを作成しない。
- AGENTS.md の生成と無関係な実装変更を行わない。
- 不明点を勝手に決定しない。

# 14. 開始

このスキルが実行されたら、Phase 1 から開始する。

最初に次の内容を質問する。

「どのようなプロジェクトを作成する予定ですか？ プロジェクトの目的、解決したい問題、最終的にどのようなものを作りたいかを教えてください。」

ユーザーの回答を受けて、順番にヒアリングを進める。
